# Installing pydive with Portable CGAL Backend

This guide explains how to install pydive with the CGAL backend in a portable way across different environments.

## Overview

pydive now provides two build options for the CGAL backend:

1. **Original CMake-based build** (requires manual CGAL installation)
2. **New standalone Cython build** (uses pkg-config or conda for CGAL detection)

Both approaches keep CGAL as the primary backend for maximum performance while making installation easier.

## Option 1: Using Conda (Recommended for Portability)

The easiest way to install CGAL portably is using conda/mamba:

```bash
# Create a new environment
conda create -n pydive python=3.8 numpy scipy cython cgal boost-cpp gmp mpfr cmake
conda activate pydive

# Install pydive
pip install .
```

Conda provides pre-built CGAL binaries, avoiding compilation issues.

## Option 2: System Package Manager

### Ubuntu/Debian

```bash
# Install system dependencies
sudo apt-get update
sudo apt-get install -y \
    libcgal-dev \
    libboost-all-dev \
    libgmp-dev \
    libmpfr-dev \
    libgsl-dev \
    cmake \
    build-essential \
    python3-dev \
    python3-numpy \
    python3-scipy \
    cython3

# Install pydive
pip install .
```

### Fedora/RHEL

```bash
sudo dnf install -y \
    CGAL-devel \
    boost-devel \
    gmp-devel \
    mpfr-devel \
    gsl-devel \
    cmake \
    gcc-c++ \
    python3-devel \

pip install .
```

### macOS (Homebrew)

```bash
brew install cgal boost gmp mpfr gsl cmake

pip install .
```

## Option 3: Manual CGAL Installation

If you need a specific CGAL version:

```bash
# Download and build CGAL
wget https://github.com/CGAL/cgal/releases/download/v5.5.2/CGAL-5.5.2.tar.xz
tar xf CGAL-5.5.2.tar.xz
cd CGAL-5.5.2
mkdir build && cd build
cmake -DCMAKE_INSTALL_PREFIX=$HOME/lib/CGAL-5.5 ..
make -j$(nproc)
make install

# Set environment variables
export CGAL_DIR=$HOME/lib/CGAL-5.5
export LD_LIBRARY_PATH=$CGAL_DIR/lib:$LD_LIBRARY_PATH
export PKG_CONFIG_PATH=$CGAL_DIR/lib/pkgconfig:$PKG_CONFIG_PATH

# Install pydive
pip install .
```

## Build System Details

### New Standalone Backend

The new `delaunay_backend_standalone.cpp` provides:

- C-compatible interface for easy Cython integration
- Standard setuptools/distutils build process
- Automatic CGAL detection via pkg-config
- Clear error messages when CGAL is unavailable

### Setup.py Detection

The updated `setup.py`:

1. Tries to detect CGAL via pkg-config first
2. Falls back to CMake-based build if pkg-config fails
3. Provides informative error messages
4. Allows building without CGAL (scipy-only mode)

## Verification

After installation, verify the build:

```python
import pydive
import numpy as np

# Test basic functionality
points = np.random.random((1000, 3)) * 100
voids = pydive.get_void_catalog(points)
print(f"Found {len(voids)} voids")
print(f"Void columns: x, y, z, r")

# Test full catalog
voids_full, dtfe = pydive.get_void_catalog_full(points)
print(f"Full catalog shape: {voids_full.shape}")
print(f"DTFE shape: {dtfe.shape}")
```

## Troubleshooting

### CGAL Not Found

```bash
# Check if CGAL is installed
pkg-config --modversion cgal

# If not found, install CGAL or set CGAL_DIR
export CGAL_DIR=/path/to/cgal
```

### Compilation Errors

Ensure all dependencies are installed:
- CGAL (with Boost support)
- GMP and MPFR libraries
- C++ compiler with C++11 support
- Python development headers

### Runtime Errors

```bash
# Add CGAL libraries to LD_LIBRARY_PATH
export LD_LIBRARY_PATH=/path/to/cgal/lib:$LD_LIBRARY_PATH

# Verify library loading
ldd $(python -c "import pydive.pydive; print(pydive.pydive.__file__)")
```

## Performance Notes

- The standalone backend has identical performance to the original CMake build
- Both use the same CGAL algorithms under the hood
- For periodic boundary conditions, use the original CMake build until standalone support is complete

## Migration from Old Build

If you were using the old CMake-based build:

1. The old `pydive.cpp` generated by CMake is still supported
2. The new standalone backend (`delaunay_backend_standalone.cpp`) is preferred for portability
3. Both provide the same Python API
4. Your existing code should work without changes
